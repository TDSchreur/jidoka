# Runs and the dashboard

How the dashboard shows your runs, and the `jidoka run` commands that agents and you use to record them.

## The dashboard

Start the dashboard and keep it running in a separate terminal: `jidoka dashboard`. Open the URL it prints (<http://127.0.0.1:4311>, or another port when 4311 is taken) to follow your runs. The dashboard follows your system's light or dark setting; use the Theme control (System, Light, Dark) at the bottom of the page to override it. The choice is remembered in your browser. While you scroll, the andon strip (what needs you) and the active runs stay at the top of the page. When the dashboard server restarts, for example after an update, an open dashboard page reloads itself within a few seconds, once no dialog or menu is open, so it always shows the running version.

One dashboard serves every Project. Running `jidoka dashboard` while one is already running prints its URL (opening on the current Project) and exits, and warns when that dashboard is a different build; it never stops it. The dashboard writes its port, pid and build to `dashboard.json` in the data folder and removes the file when it stops; `jidoka run` reads it to find the dashboard, and a file whose dashboard no longer answers counts as no dashboard. `jidoka dashboard --port <port>` picks the port (an error when it is taken) but does not create a separate dashboard: the data folder always has one.

## Starting a run with its workspace

`jidoka run begin "<title>"` creates a run and its workspace in one command. The workspace is a git worktree on a new branch, made from the pull request base branch. It replaces `jidoka run start`, the `git worktree add` and the `jidoka run update` that records them; `jidoka run start` still works as before.

```text
jidoka run begin "<title>" [--agent <codex|claude|copilot>] [--mode <full|balanced|fast|jidoka-full|jidoka-balanced|jidoka-fast>]
                  [--base <branch>] [--branch <name>] [--json]
jidoka run begin --run <run-id> [--base <branch>] [--branch <name>] [--mode ...] [--agent ...] [--json]
```

- **Base.** `--base` names the branch. Without it the command uses the branch `refs/remotes/origin/HEAD` points to. It fetches that branch from `origin` and creates the worktree from `origin/<base>`; the recorded base commit is that commit. It does not read the project's documentation, so an agent passes the project's documented base itself.
- **Names.** `--branch` is used as given. Without it the branch is a kebab-case name from the title (ASCII letters and digits, at most 40 characters), with `-2`, `-3` and so on added until neither a branch nor a folder uses the name. The worktree is `<repo-parent>/<repo-name>.worktrees/<branch with / replaced by ->`, beside the main checkout, wherever the command runs. An explicit branch or folder that exists stops the command, and the retry command it prints leaves `--branch` out, so the retry picks a free name and never takes over what exists.
- **Recorded.** Mode, worktree, branch and base commit, the repository (as `run start` records it) and the agent session, with the stage set to define and the activity "Workspace ready". It prints the run ID first, then worktree, branch, base and base commit, and then the Define stage's instructions as `jidoka run next <id>` prints them, so the agent can start without another command; `--json` prints the same, plus `gitignore_added`, `gitignore_warning`, `session_warning` and `next` (the `run next --json` object). With a session warning it prints no instructions, because the agent should stop first, and it does not record the warned session on the new run, so the old session's usage is never counted for it; the session that continues the run records itself with its first `jidoka run update`.
- **One session per run.** A session that coordinates several runs keeps growing, and every turn re-reads its whole context, so later runs get expensive. When the current agent session is already recorded on another run, of any status, the output carries a `Warning:` line naming that run's id and title and the command for a fresh session (`--json`: `session_warning`, null otherwise). Jidoka reads the session from `CLAUDE_CODE_SESSION_ID` (Claude Code, `/clear`), `CODEX_SESSION_ID` or `CODEX_THREAD_ID` (Codex, `/new`) and `COPILOT_AGENT_SESSION_ID` (Copilot CLI, `/clear`). The workflow skills stop and ask the user when the warning appears, and the Finish report reminds the user to start the next run in a fresh session. A resumed run is not counted against itself, and a failure to list runs gives no warning.
- **Ignored folders.** After the run is recorded, the worktree's `.gitignore` gets `.jidoka/` and `.scratch/` when they are missing (the file is created if absent). It is left uncommitted: the output lists the added entries (`--json`: `gitignore_added`), and the agent commits `.gitignore` with its first commit. When the file cannot be updated (for example it is a symlink or unreadable), the output carries a warning (`gitignore_warning`) and the run continues.
- **Failures.** Once the run exists, a missing `origin`, an unknown base, a failed fetch, git that cannot write, or a name that is taken mark the run blocked with the reason, print the reason and the command to retry, and exit with status 1. Outside a repository, inside another `.git` folder (a submodule), or with a bad option, no run is created. Nothing is ever deleted, reset, checked out over or cleaned.
- **Retry.** `jidoka run begin --run <id>` resumes that run. The command to retry that a failure prints carries `--branch <name>` as soon as a name was chosen; a resume takes over an existing branch or worktree only when it is given that branch, and without one it picks a free name like a new run, so it never takes over another run's workspace. If nothing was made it does everything; a branch without a worktree gets its worktree; a clean worktree that was made but not recorded is recorded. Anything else (a folder that is not a worktree, a branch with commits of its own, a worktree with uncommitted changes) stops and says exactly what it found. A worktree that git lists but whose folder is gone is reported, and you run `git worktree prune` yourself. A run that is finished, or already has a workspace, is refused.
- **Dedicated worktrees.** When your agent environment hands you a fresh worktree, the Workspace procedure still uses `jidoka run start` and `jidoka run update` by hand; `begin` always makes its own worktree.

## Reporting runs manually

For manual tracking, `jidoka run start "Task title"` prints a run ID (add `--agent claude`, `--agent codex` or `--agent copilot` to say which agent the run is in; model routing needs it when the policy file covers several agents), and `jidoka run update <id>` reports its progress. Stages are `define`, `build`, `check`, and `finish`; statuses are `running`, `blocked`, and `done`.

### Run context

Besides its stage and status, a run records the context a new session needs to continue it. Record it through the CLI. The run holds references and short summaries, not transcripts or secrets:

| Option | Records |
| --- | --- |
| `jidoka run start` | The canonical `repository` (the main checkout, the same from every linked worktree) next to the folder the run started in. |
| `--worktree <absolute-path>`, `--branch <name>`, `--base-commit <sha>` | Where the run's work lives and the commit it started from. |
| `--mode <full\|balanced\|fast\|jidoka-full\|jidoka-balanced\|jidoka-fast>` | The workflow mode. |
| `--spec <http(s)-url\|path>`, `--pr <http(s)-url>` | The spec (a URL or a local path) and the pull request. URLs with credentials are refused. |
| `--ticket "<reference> <title>"` (repeat), `--ticket-status <reference>=<pending\|in-progress\|done>` | The ordered ticket list, listed whole each time (statuses of kept tickets are preserved), and its progress. At most one ticket is in progress. |
| `--unticketed`, `--clear-tickets` | Explicitly declare work without tickets, or remove the ticket plan entirely. Listing tickets replaces an unticketed plan. |
| `--run-report <skill\|activity> "<text>"` (repeat) | Append a short report to the run, with the current stage and server time. |
| `--ticket-report "<reference>" <skill\|activity> "<text>"` (repeat) | Append a short skill or activity report to a listed ticket, with the current stage and server time. |
| `--finding <check> <location\|-> "<text>"` (repeat) | Record an issue a check reported as an open [Finding](../GLOSSARY.md), in Check or in Build during a Rework (a late check result joins the current Rework). `<check>` is a check name from the catalog (the ones `run next` lists); `<location>` is `-` when there is none. Findings get the ids F1, F2, ... per run, and Jidoka captures the reviewed commit (the worktree's HEAD) and the time. Starting a Rework associates its open Findings with the assigned Rework number. Text and location are at most 500 bytes; at most 100 per update and 1,000 per run. |
| `--finding-status <id>=<open\|fixed\|dismissed\|deferred>[:<reason>]` (repeat) | Set a Finding's outcome. `dismissed` and `deferred` need a reason (at most 500 bytes); `open` and `fixed` refuse one. `fixed` records the worktree's HEAD as the fix commit. Allowed in Check (any state) and in Build during a Rework (`fixed` only). |
| `--summary <stage>=<text>` | A short summary per stage, kept after later stages begin. |

Skills are also recorded without a report: recording the mode adds the workflow skill, and the dashboard reads the agent's session log for the sessions of the run and adds each skill the agent used (Claude Code's `Skill` tool, Copilot's `skill` tool, and a Codex command that reads `<name>/SKILL.md` with `cat`, `sed`, `head` or a similar reader, not one that only lists, searches or edits it) to the stage it was used in, from five minutes before the first stage (the workflow skill is loaded just before the run starts). Only the skill's name and time are kept. A skill used while another run was active in the same session is left out, because it cannot be assigned. This needs the dashboard to be running, like usage tracking.

Options left out keep their value, each has a `--clear-*` form (`--clear-tickets`, `--clear-summary <stage>`), and an inconsistent update is refused with the reason and changes nothing.

`jidoka run next <id>` prints what the run does now: the current stage, its instructions, the open gates, the allowed moves (next stage and Rework), the stored summaries and tickets, and the stage's routed model and effort (`--json` for the same as data). In Check it also lists applicable and skipped checks, delivers the applicable checks’ instructions, and shows their gates and any model routes. Check selection requires a readable diff from the recorded base commit to HEAD. Guidance and the dashboard show the same local gate blockers as advance. The CI gate shows "Awaiting live check" before Finish evaluates it.

`jidoka run gate <id> <gate> <pass|fail> [--evidence "<text>"]` records a result for the current stage and Rework. Record `verified` after full verification; the command captures the worktree's HEAD. Fast requires it in Build; Balanced and Full require it in Check on the final reviewed candidate and current Rework, rather than on each Build exit. In Check, record `checks-recorded` for each applicable check using `--check <name>` after it completes and `no-actionable-findings` when their findings have been resolved; it is refused while any Finding is open, and the error names the open ids. A later result for the same gate replaces the earlier result for advancement. An open Finding blocks Check even after a recorded pass. Ticket completion, the Finish summary and CI are checked automatically.

Build requires a ticket plan in every workflow mode. List all tickets or explicitly declare `--unticketed`. An empty or cleared list leaves Build without a ticket plan. Mark a listed ticket active with `--ticket-status <reference>=in-progress`. In Full, commit and verify the ticket's work, then record `jidoka run gate <id> tickets-verified pass` while that ticket is still active. The pass covers that work attempt and commit. The verified commit must remain in the history of the Build candidate. Reopening or removing and re-listing a ticket requires a new pass. Rework retains the passes for unaffected tickets. In unticketed Full Build, use the same gate after verifying the current HEAD, including each Rework.

`jidoka run advance <id>` checks the current stage's gates and moves to the next stage, or marks Finish done. On success it prints `Advanced run <id>` and then what `jidoka run next <id>` prints for the new stage, so the agent needs no separate `run next`; `--json` prints only the `run next --json` object. A done run has no stage instructions. `--summary <stage>=<text>` and `--activity <text>` are saved with the successful transition. A failed gate leaves the run unchanged and gives the command to resolve it. Include the summary and activity again when retrying. `jidoka run advance <id> --force --reason "<text>"` skips the gates when they cannot be met, still follows the stage graph, and records "Forced advance from <stage>: <text>" as a run report; `--force` needs a reason and a reason needs `--force`. A run's stage changes only through `run advance`, apart from a Rework. The `verified` gate must match the current HEAD. Normal Finish completion requires a nonblank Finish summary and an open pull request whose head matches the worktree and whose CI passed or has no checks. Forced completion also requires a Finish summary and records its explicit reason. CI is read from GitHub or Azure DevOps. If no checks appear, the command waits through the 90-second discovery period before accepting that the project has no CI.

`POST /api/runs/<id>/advance` accepts optional `summaries` keyed by stage, `activity` text, `sessions` IDs and `agent_homes` (agent home folders keyed by `claude`, `codex` or `copilot`, see [token usage](usage-tracking.md#token-usage)) with the transition request. The body can also include `force: true` with a `reason`. These changes are saved together with the transition.

The dashboard and `jidoka run next` show recorded stage exits with their Rework number, outcome and gate evidence. A forced exit shows its reason and the gates it bypassed. A merge-reconciled Finish records the observed merge and shows CI as bypassed. A rejected move creates no exit record. Changes to tickets, Findings or summaries never alter earlier exits. Runs saved before this feature have exit evidence for transitions made after the upgrade.

`jidoka run inspect <id>` prints a run's context, including its Findings with their check, location, text, reviewed commit, Rework, outcome, reason and fix commit (`--json` for the stored record, where they are the `findings` list). The dashboard shows a run's detail as a route card that follows the run along Define, Build, Check and Finish (the worktree and base commit stay in `jidoka run inspect`), shows a Model routing table with the model and effort requested per stage next to what the usage shows (the same comparison as `jidoka run inspect`, with a "Mismatch" label when they differ), shows ticket progress and pull request and spec links on each run's row, and counts the runs of every linked worktree under their repository. A local spec or ticket (a recorded reference that is not an http(s) link, for example from the local tracker) gets a View link, and a local ticket's title opens it, in the Reader: a dialog over the detail that shows the Markdown file rendered. Agents record such references as absolute paths so the dashboard can find them.

On screens of 1280 px and up the run detail shows two columns: the route on the left and the facts of the run on the right (change group, stage gates, check selection and model routing). Narrower screens show one column with the facts above the route. A run in a change group has a "Change group" section there with the group's title, summary and spec, its runs (a run on this dashboard opens its own detail), what this run waits on and its milestones.

To continue a run in a new session, ask the agent to continue it by ID. The workflow skills then read the context and check the recorded repository, worktree, branch, base commit and Git state, report any difference, and never reset, clean or discard work to make them match.

`jidoka run check <run-id>` compares what the run records with the repository, so a new session can see at once whether it is safe to continue. It only reads: it never fetches, resets, cleans, checks out, deletes or commits. Git runs without optional locks and without lazy fetches in a partial clone, and with `core.fsmonitor` and `log.showSignature` turned off, so the fsmonitor hook and signature checks do not run. Clean and process filters that the repository sets can still run during `git status`, as they would for any `git status` there, so run the check only on repositories you trust.

```text
jidoka run check <run-id> [--json]
```

It runs five checks and reports each as `matches`, `differs` with what it found, or `unknown` when the run never recorded the field. A check that needs the worktree is `not-checked` when the worktree is missing or differs. A git command that fails during a check also counts as `differs`, with git's message.

| Check | Matches when |
| --- | --- |
| `repository` | The recorded repository exists, and `git rev-parse --git-common-dir` gives the same directory there as in the worktree. |
| `worktree` | The recorded worktree exists and `git worktree list --porcelain` of the recorded repository lists it. |
| `branch` | `git branch --show-current` in the worktree is the recorded branch. A detached HEAD differs. |
| `base-commit` | The recorded base commit is a commit id (4 to 64 hexadecimal digits), the repository has it, and `git merge-base --is-ancestor <base commit> HEAD` succeeds. |
| `working-tree` | `git status --porcelain` is empty. Otherwise the changed paths are listed. |

Commits of `HEAD` that no remote-tracking branch has (as of the last fetch) are listed as not pushed, which does not count as a difference. A repository without remote-tracking branches says the list is not known. The exit status is 0 when nothing differs, also when some fields are unknown, 2 when a check differs, and 1 for a problem such as bad arguments or an unreachable dashboard. `--json` prints the same data (`run`, `consistent`, `exit_code`, `checks` with `check`, `state`, `recorded` and `found`, `changes`, `unpushed` and, when the list is not known, `unpushed_unknown`).

`jidoka run sync <run-id>` reads the state of the run's pull request from its host (`gh` for GitHub, `az` for Azure Repos) and brings the run in line with it: a merged pull request clears the activity, completes a run in Finish, and keeps its existing Finish summary or records "Pull request merged", a closed one clears the activity and blocks the run with "PR closed without merge", and an open one changes nothing. A host that cannot be reached is reported and leaves the run as it is. The dashboard does the same on its own for every run with a pull request, and the run sheet has a "Check PR" button to do it at once. `jidoka pr wait` does it when it reports that the pull request is no longer open.

```text
jidoka run sync <run-id> [--json]
```

`--json` prints `run`, `pull_request`, `state` and `run_updated`.

`jidoka run cleanup <run-id>` removes the worktree and local branch of a run after its pull request merged, so you do not clean up by hand. Run it from the main checkout, not from inside the worktree. A directory at the recorded worktree path that git does not list as a worktree is left alone: the command says nothing was removed and names it, and the run's record is still cleared.

```text
jidoka run cleanup <run-id> [--discard [--force]]
```

It reads the pull request state fresh and refuses, with exit status 1 and nothing removed, unless the pull request is merged. It also refuses when the run records no pull request, when the pull request comes from another branch than the run's recorded branch, when the run records a worktree but no branch (nothing ties that worktree to the pull request), when the worktree is detached or on another branch, when the worktree has uncommitted changes, when the local branch is not at the head commit of the merged pull request (it may hold commits that were never pushed), when your current directory is inside the worktree, when the worktree is locked, when the branch is checked out in any other worktree (the main checkout included; checked before anything is removed), and when the recorded repository or worktree path is relative. Otherwise it runs `git worktree remove` (without `--force`; for a worktree directory you deleted by hand it drops only that registration, and other stale worktrees are left alone) and checks that git no longer lists it (a recorded worktree directory that exists but is not registered with git is reported as left alone, not removed). The worktree is deleted with everything in it, gitignored files such as `.env` or build output included, so copy out what you need first. Then it deletes the branch with `git update-ref -d`, pinned to the commit it checked (a squash merge needs a forced delete, and a branch that moved since the check is kept), in the run's repository. The remote branch is left alone. The run stays on the dashboard with its worktree and branch cleared and the activity "Cleaned up worktree and branch"; its stage and status are kept. Running it again finishes what is left and reports what was already gone.

`--discard` removes the worktree and local branch of a run whose pull request did not merge: one that was never opened, or was closed ([ADR-0024](adr/0024-run-cleanup-discard-removes-unmerged-work-only-on-request.md)). It refuses, removing nothing, while the pull request is still open or a draft (close it first). It also refuses, listing them, when the worktree has uncommitted changes or the branch has commits that no remote-tracking branch has (as of the last fetch). `--force`, which needs `--discard`, removes them anyway, so copy out what you need first. The refusals that do not depend on the pull request stay: a locked worktree, a current directory inside the worktree, a branch checked out in another worktree, a worktree on another branch, and relative or invalid recorded names. The run stays on the dashboard with the activity "Discarded worktree and branch"; delete the run from its detail when you no longer need the record.

Report progress and request a transition with these commands.

```sh
jidoka run update <id> --activity "Implementing ticket #42" --ticket-status "https://github.com/owner/repo/issues/42=in-progress"
jidoka run update <id> --ticket-report "https://github.com/owner/repo/issues/42" skill "jidoka-tdd" --ticket-report "https://github.com/owner/repo/issues/42" activity "Tests passed"
jidoka run block <id> --reason "Waiting for credentials"
jidoka run resume <id> --source "User supplied credentials"
jidoka run update <id> --finding code-review src/main.rs:42 "Unchecked index panics on empty input"
jidoka run rework <id> --finding F1=behavior --finding F2=wording
jidoka run advance <id> --summary finish="<what was completed>"
```

Omitted fields keep their stored values. `jidoka run update` reports metadata and can initialize the workflow mode once. Setting the same mode again is allowed. Use `--clear-activity` to clear the activity. Activity, block reasons, resume sources and Rework decisions must be nonblank and at most 2,000 bytes. A ticket reference must be an HTTP(S) URL, local path or identifier of at most 4,096 bytes without spaces. `--agent-home <agent>=<absolute-path>` records the home folder of agent `claude`, `codex` or `copilot`, where the run's [token usage](usage-tracking.md#token-usage) is read; the commands that record a session record its agent home on their own.

`jidoka run block` requires a running run and `jidoka run resume` requires a blocked run. Their events include the stage, time, reason and source. `jidoka run rework` requires a running run in Check and one `--finding <id>=<wording|behavior>` for every open Finding, each exactly once. The server assigns the next [Rework](../GLOSSARY.md) number. The agent classifies the proposed fix for each Finding. The Rework counts as `behavior` when any Finding is `behavior`, whatever the order, and then Rework 3 needs the user's authorization with `--decision`, as does any Rework after 3 ([ADR-0006](adr/0006-limit-reworks-and-gate-late-ones-on-the-user.md)). A request that misses, repeats or names a Finding that is not open is rejected before anything changes, and the Run stays in Check. After success it prints the Build instructions.

`POST /api/runs/<id>` accepts metadata such as `activity`, `tickets` and `ticket_status`. Use `"unticketed": true` to declare unticketed work or `"tickets": null` to clear the plan. Run responses show each ticket's `status` and `work_attempt`, plus `unticketed_attempt` when explicitly unticketed. Omit a field to preserve it, send a value to replace it or send `null` to clear a clearable field. `sessions` adds agent session IDs, and `agent_homes` records agent home folders keyed by `claude`, `codex` or `copilot`; each must be an absolute path and replaces the one recorded for that agent. `POST /api/runs` accepts `session` and `agent_homes` the same way when it creates a run. Unknown fields, including the old `status`, `blocking_reason`, `rework` and `current_ticket` update fields, are rejected.

Use the authenticated `POST /api/runs/<id>/lifecycle` endpoint to block, resume or start a Rework.

```json
{"action":"block","reason":"Waiting for credentials"}
{"action":"resume","source":"User supplied credentials"}
{"action":"rework","findings":[{"id":"F1","classification":"behavior"},{"id":"F2","classification":"wording"}],"decision":"User approved the behavior fix"}
```

Send one object per request. Responses include the updated run. The server owns `rework`, `block_source`, and `rework_history`. Each Rework history entry records the time, number, the classified Findings, the overall classification plus the recorded decision when present. Older records keep their stored counter and may have no historical entries.

The dashboard’s **Needs you** indication includes blocked runs that may require attention. These appear first on the line, count in the page title and drive the andon strip, its filter and opt-in browser notifications. Automatic context compaction stays blocked and displays its reason on the line and in the run detail until agent activity resumes. Both `GET /api/runs` and `GET /api/runs/<id>` return the derived `needs_you` boolean alongside the recorded status.

Run details list every pass through a stage (each Build and Check, including Reworks) with its start time, duration and the activity it started with. Run reports are displayed in the last pass of the stage they were filed under that had started by then (the nearest pass of that stage otherwise; by time for older runs that recorded no stage), including when no tickets exist. Ticket reports are displayed under their ticket in run details when that pass lists the ticket, and in the pass otherwise. When a run is blocked or resumed, run details show a "Blocked: <reason>" or "Resumed" line in the pass that holds it; `jidoka run inspect` lists them under "Events" (`events` in `--json`); events that match no pass show under "Other reports". Pauses the agent's log shows (see [Pauses and requests for attention](usage-tracking.md#pauses-and-requests-for-attention)) and idle gaps appear the same way. They are agent-reported and may be incomplete; no reports does not mean no work occurred. Each report is limited to 500 bytes; run and ticket reports are each limited to 100 per update and 1,000 per run. Do not report secrets or transcripts.

Run responses and `runs.json` include the stored metadata and `updated_at`, a server-owned Unix timestamp in milliseconds set on creation and each successful update. Callers cannot set `updated_at` through an update. Existing records load with `null` for missing metadata and timestamps; they receive a timestamp on their next update. The timestamp records a run update, not an agent heartbeat. Upgrade the CLI, refresh the installed skills and restart the dashboard together. Update scripts and automation to use the new commands and request bodies before resuming existing runs. The dashboard shows these fields on each run's row on the line. Done runs are listed under Completed, grouped by day. Inspection and the run detail show how Jidoka finished. The server-owned `completion` field records a confirmed head and CI outcome, an observed pull request merge, or an explicit override reason. Earlier done runs may have no recorded completion reason. Next to each pull request link the dashboard shows its state (Open, Draft, Merged or Closed). The dashboard server reads it in the background, with `gh` for GitHub and with `az` and its `azure-devops` extension for Azure Repos, stores it on the run as `pr_status`, and reads it again about once a minute until the pull request is merged. Without the tool, or when it is not signed in, the state is unknown and the run's detail says why. Callers cannot set `pr_status`. A run is deleted from its detail, and Clear completed removes all completed runs, each after a confirmation; deleting removes only the run record, not its worktree or pull request. The record is removed by `DELETE /api/runs/<id>`, which needs the session token from the dashboard page (sent as `X-Session-Token`), so it works from the dashboard only.

`POST /api/runs` and `POST /api/runs/<id>` need the CLI token, sent as `X-Jidoka-Token`. The dashboard page's session token is refused there, so reading the page grants no write access. A missing or wrong CLI token gets 401; a refused Host, Origin or content type gets 403. The dashboard writes a new CLI token on each start to `session-token` next to `runs.json` in the data folder above. On Linux and macOS the file is mode 0600, and the folder is made 0700 when the dashboard creates or owns it (a symlinked folder is left as it is, with a warning on stderr when its target is accessible to group or others; run `chmod 700` on it; a dangling symlink stops the dashboard from starting); if it cannot be made private the dashboard fails to start; on Windows the file relies on the per-user access rules of `%LOCALAPPDATA%`. The `jidoka` CLI reads the file on each request, so it keeps working across dashboard restarts. If the file is missing or the server answers 401, the CLI says to start or restart `jidoka dashboard`. If the dashboard cannot write the file, it prints the path and the error and exits with a failure. The token never appears in an error or a response. After upgrading, restart the dashboard with the updated CLI: an older dashboard or CLI on either side makes POSTs fail.

## Change groups

A change can touch several repositories and need several pull requests. A **change group** links ordinary runs to one shared spec, so the related runs can be found together. Group membership leaves each run's stages, gates, verification and cleanup as they are. Start a run as usual and attach it with `jidoka group add` once you know what else the change touches.

| Command | Purpose |
| --- | --- |
| `jidoka group create "<title>" --spec <url\|path> [--run <id>]...` | Create a group and print its ID (`g` and digits). The spec is a durable web link, such as a tracker issue, or a local file, which is stored as its absolute path. Every `--run` is checked before anything is saved. |
| `jidoka group list [--json]` | List the groups, across sessions and checkouts. |
| `jidoka group inspect <group-id> [--json]` | Show the spec, the members with their repository, pull request and the stored pull request state with its last check time, and a summary such as `2 of 3 attached PRs merged`. |
| `jidoka group add <group-id> <run-id>` | Attach an existing run. A run is in at most one group. |
| `jidoka group remove <group-id> <run-id>` | Detach a run. This also detaches a member whose run record is gone, which `group inspect` shows as `run missing`. |
| `jidoka group delete <group-id>` | Delete a group that has no runs. |
| `jidoka group milestone add <group-id> "<text>"` | Create a pending milestone, a named condition such as "Bicep module v2.4.0 published", and print its ID (`m1`, ...). |
| `jidoka group milestone remove <group-id> <milestone-id>` | Delete a milestone that no dependency refers to; otherwise list the dependencies to remove first. |
| `jidoka group depend <group-id> <run-id> --on-pr <run-id>` | Make a run wait on another member's pull request being merged, and print the dependency ID (`d1`, ...). |
| `jidoka group depend <group-id> <run-id> --milestone <milestone-id>` | Make a run wait on a milestone of the group. |
| `jidoka group undepend <group-id> <dependency-id>` | Remove one run's dependency; other runs waiting on the same milestone keep theirs. |
| `jidoka group confirm <group-id> <milestone-id> [--evidence <url>]` | Record that a milestone happened, for every run that waits on it. Stores the time and the optional `http(s)` evidence URL, not who confirmed. A confirmed milestone is refused until you reopen it. |
| `jidoka group reopen <group-id> <milestone-id>` | Return a milestone to pending for every run and clear its time and evidence. |

`jidoka run inspect` shows the group of a grouped run (`group` in `--json`); an ungrouped run's output is unchanged. A run that belongs to a group cannot be deleted from the dashboard: the server answers 409 and names the `jidoka group remove` command to run first. A cleaned-up run keeps its record, so it keeps its place and its recorded pull request state in the group.

`group inspect` and the dashboard read the pull request state the dashboard server already stored. They neither ask the host nor touch a worktree. The state counts only while it belongs to the run's current pull request URL; otherwise the member shows as `unchecked`. The decisions behind groups are in [ADR-0012](adr/0012-change-groups-link-runs-through-a-server-owned-groups-file.md).

Dependencies are advisory: `group inspect` lists them under the run that waits, `jidoka run next` shows them in Finish, and nothing blocks on them. Both ends of a dependency must be members of the group, a run cannot wait on its own pull request, pull request dependencies cannot form a cycle, and `group remove` refuses a run that still waits or is waited on, listing the dependencies to remove first. A pull request dependency clears only when the upstream run has a current pull request URL and the stored state for that same URL is merged. Right after the URL changes, the dependency is pending and `unchecked` until the replacement has its own status. A merged pull request never confirms a publication or deployment milestone. `group inspect` summarizes `2 of 3 attached PRs merged, 1 milestone pending`, counting each pending milestone once; see [the multi-repo guide](multi-repo.md) for the whole workflow and [ADR-0013](adr/0013-group-dependencies-are-advisory-conditions-stored-in-the-group.md) for the rules.

The dashboard shows groups in a Change groups section below On the line, with one row per group: its title, a summary such as `1 of 3 attached PRs merged, 1 milestone pending` and the spec (a link for a web spec, plain text for a local path). Select the title (a button; Tab to it and press Enter or Space) to list the member runs with their repository, pull request link, the pull request state in the same words as `group inspect` and, when a state was read for the current URL, when it was last checked. Each dependency shows what it waits on, its status and whether it is cleared or pending, and each milestone shows when it was confirmed, its evidence link and the runs waiting on it. Runs stay in their repository views: the section is read-only and does not change the run counts, the andon strip or the project menu counts. A dashboard that cannot read `/api/groups` (an older server) hides the section.

The CLI changes groups through `GET /api/groups`, `GET /api/groups/<id>`, `POST /api/groups`, `POST /api/groups/<id>/add`, `POST /api/groups/<id>/remove`, `POST /api/groups/<id>/delete`, `POST /api/groups/<id>/milestones`, `POST /api/groups/<id>/milestones/remove`, `POST /api/groups/<id>/depend`, `POST /api/groups/<id>/undepend`, `POST /api/groups/<id>/confirm` and `POST /api/groups/<id>/reopen`. The POSTs need the CLI token like every other POST, and the delete is a POST because the dashboard's `DELETE` needs the page's session token.

## Security

The server listens only on localhost but has no user authentication. Other users on the same machine can read and change run titles and project paths; use it only on a trusted machine.
