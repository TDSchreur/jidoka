# Checking readiness

`jidoka doctor` reports whether the current repository and your machine are ready for Jidoka, without changing anything, installing anything or starting the dashboard, unless you ask it to create the model-routing policy file (see below). It checks:

- the project: a Git repository, an `origin` remote, origin's default branch (`git remote set-head origin --auto` sets it when unknown), the setup output of `/jidoka-setup` (`docs/agents/issue-tracker.md` and the `## Agent skills` section), which `/jidoka-full` always needs and the lighter workflows only when they read or publish specs or tickets, and the verification commands listed as bullets under `## Commands` in `AGENTS.md` or `CLAUDE.md`. It looks for each command's tool but never runs it. In a Rust project (a `Cargo.toml` at the root) on a non-Windows machine, a `windows-lint` check asks `rustup target list --installed`: it passes when a Windows target is installed, is a warning that never blocks when none is (fix: `rustup target add x86_64-pc-windows-gnu`, so verification can lint Windows-only code), and is `skipped` when rustup is not available.
- each agent (Codex, Claude Code, Copilot): its command is on `PATH`, and every file of every skill `jidoka install` bundles is installed in the folder `jidoka install` would use (honoring `CODEX_HOME`, `CLAUDE_CONFIG_DIR` and `COPILOT_HOME`). With `--config-dir`, Claude Code gets one `skills` check per folder, each naming its path.
- the skills version, a `skills-version` check in the project section, only when an install record exists: it passes when the record's version matches this binary and is a warning (never blocking) when it differs, including a record adopted from an earlier install without a version. Fix: run any `jidoka` command or `jidoka install`. Without a record there is no such check.
- the pull request host, in a "Provider" section after the agents. `host` says whether origin is on GitHub or Azure Repos, worked out the way `jidoka pr open` does it (including `jidoka.prProvider`). An unknown host, or an override that does not match origin, is a warning that says to open pull requests with the host's own tooling; without an origin the section is `skipped`. For GitHub, doctor looks for `gh` on `PATH` and runs `gh auth status`. For Azure Repos, it looks for `az`, runs `az extension show --name azure-devops`, and counts you as signed in when `AZURE_DEVOPS_EXT_PAT` is set or `az account show` succeeds. It only checks that the variable is set, never reads or prints the token, and discards what these commands print. A `not-verified` line says what it did not check: whether the token is valid, project permissions and branch policies. A missing tool or sign-in is a warning, so this section never changes whether Jidoka is ready.

- the [model routing](model-routing.md) policy, only when a `model-routing.json` exists and is switched on. A "Model routing" section follows the provider section. Doctor asks the agent for its `--version` there, using the program's absolute path from `PATH`; that is the only agent command it runs, and it calls no model.
  - `policy`: the file loads. A file that stops `jidoka run start` is a `fail`, which includes a Stage without a model and a mistake in any enabled entry, named as `agents.<agent>`. With the `agents` form, the line says which agents the file configures, and each agent's checks that follow are tagged with it, as `host [claude]` in the text and an `agent` field in `--json`.
  - `jidoka doctor` checks every configured entry. `--agent claude`, `--agent codex` or `--agent copilot` checks only that agent's entry: an agent with no entry, or a switched-off entry, is `skipped` with the reason. With no `--agent`, an agent without an entry is left out.
  - `host`: for Claude Code, the command is on `PATH` and is version 2.1.292 or later, the first with the Agent tool's `effort` option. For Codex and Copilot CLI, the command and its version are shown, but Jidoka does not know which version first supports a model and effort per subagent, so that is `skipped`.
  - `model` and `effort`: for Claude Code, each routed Stage must name `opus`, `sonnet`, `haiku` or `fable`, the only models the Agent tool accepts, and an effort of `low`, `medium`, `high`, `xhigh` or `max`. A Stage without an effort is flagged, because the model's default applies and differs between models. Which levels a particular model offers is not checked. For Codex Jidoka keeps no list of models that are available, so both are `skipped`. For Copilot CLI the `model` line passes when the entry loads (the policy check above rejects Claude Code aliases and efforts Copilot CLI does not list), and says that whether the account can use the models is not checked, so compare the models `jidoka run inspect` observed; `effort` is a warning for a Stage without an effort, because the model's default applies.
  - `overrides`: for Claude Code, a warning when `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` together with `CLAUDE_CODE_SUBAGENT_MODEL`, or `CLAUDE_CODE_EFFORT_LEVEL`, is set in the environment, your Claude Code `settings.json`, or the project's `.claude/settings.json` or `.claude/settings.local.json` (their `env` entries), because they replace the policy's model or effort. Only string values are read, and enterprise-managed settings are not, so an override set there is missed. A settings file that cannot be read is `skipped`.

Each line is `pass`, `missing` (something to supply), `fail` (something broken), `warning` (a risk to read about that does not stop Jidoka) or `skipped` (not checked, with the reason), with a fix where there is one. Model routing problems other than a policy file that cannot be used are warnings, because model routing is optional and without it a stage uses the session's model. The exit status is 0 when the project checks pass and at least one agent is usable, and the model-routing policy, if there is one, loads. Use `--agent codex|claude|copilot` to check, and require, one agent, and `--json` for structured output.

Doctor writes a starter model-routing policy only when you ask. The installer and updater create the same three-agent policy if it is missing. `jidoka doctor --create-model-routing` creates `model-routing.json` in the config folder with an entry for Claude Code, one for Codex and one for Copilot CLI, each routing all four Stages with the starter models above. Add `--agent claude`, `--agent codex` or `--agent copilot` for an entry for that agent only. The Copilot CLI entry uses `claude-sonnet-5.5` and `claude-haiku-4.5`. Doctor then runs its checks, so the new file is verified straight away. Giving the option is the confirmation: there is no prompt. The file is switched on, so the next run uses it. Edit the models and efforts, or set `"enabled": false` to switch it off. Anything already there, including an unreadable or invalid file and a symbolic link, is left unchanged, and doctor never writes through a symbolic link. If it cannot write the file, it stops with the reason and does not run its checks. With `--json`, the note about the file goes to stderr and stdout stays JSON.
