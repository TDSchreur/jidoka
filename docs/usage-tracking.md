# Token usage and request analysis

Jidoka reads the session logs your agents already write, to show what each run cost and where its model requests went.

## Token usage

The dashboard reads the token counts your agents write to their own session logs and shows them per run, stage, model and ticket. It also estimates the cost from a built-in price table (see below), and it keeps only counts, identifiers and the reasoning effort of each call: no conversation text, prompts, tool output or credentials are stored.

- `jidoka run stats <id>` prints the breakdown (stage, model and ticket, with the rework and work with no ticket in their own rows), the totals per model, and what the figures do not cover. `jidoka run stats --all` adds the totals per model over all runs and names the runs it leaves out.
- The dashboard shows the fresh tokens on a run's row and the breakdown in the run's detail: per row, per model (fresh tokens, cache reads and estimated cost) and per stage.

**What the figures mean.** Every agent is normalized to the same four counts:

| Count | Meaning |
| --- | --- |
| Input | Input tokens that were not read from the cache. |
| Cache read | Input served from the cache. |
| Cache write | Tokens written to the cache. |
| Output | Output tokens, including reasoning tokens where the agent counts them in output. |

**Fresh tokens** are the headline figure: input excluding cache reads, plus cache writes and output. Cache reads are shown beside them, not inside, so large cached contexts do not hide the work. Reasoning is shown as "of which" and is never added to output twice. Codex and Copilot report cached tokens inside their input; the dashboard takes them out so all agents compare. A count an agent does not report is `n/a`, never zero.

**Estimated cost.** `jidoka run stats` and the dashboard show an estimated cost per row, model, stage and run. It is a token-based estimate at API list prices, not what a ChatGPT/Codex or Claude subscription is charged: input, output, cache reads and cache writes times the model's price per million tokens in USD. The prices are built into Jidoka (`src/cost.rs`, with their source and date) and cover the Claude models listed there and the OpenAI models for which OpenAI publishes a Standard-tier price (https://developers.openai.com/api/docs/pricing, read 2026-11-10). For Codex, `input_tokens` include the cached tokens, which Jidoka splits out and prices at the cached-input rate; reasoning tokens are part of output and billed as output. A request with more than 272,000 input tokens (cached included) is billed at the long-context rates of the models that list them (gpt-6.x, gpt-5.6-x, gpt-5.5, gpt-5.4); Jidoka stores that part of each row's tokens with the row. Codex does not say which cache retention a cache write used, so a row of an OpenAI model with cache writes is `unknown`. The cost is computed when you look, never stored: a price change applies to existing runs. A model without a price (such as `codex-auto-review`, `gpt-5-codex` or `gpt-5.1-codex`) shows `unknown`, never `$0.00`, and a total that includes one shows `>= $X (partial)` with the unpriced models named; if nothing is priced the total is `unknown`. A row that reported neither input nor output is `unknown` too. Discounts and Priority, Flex, Batch or regional pricing are not applied. In the API (`/api/runs`), unknown costs are `null`.

**How a session is tied to a run.** Folder and time are never enough on their own. A session counts for a run when its id was recorded on the run, or its log holds a `jidoka run update`, `inspect`, `stats`, `check`, or `jidoka pr open`, `sync` or `wait` command naming the run's id (the id elsewhere in a log, such as in a listing, does not count). `jidoka run start` and `jidoka run update` record Claude Code's session id automatically; for another agent, pass `--session <id>` when you know it. Within a session, each log entry goes to the stage, rework and ticket the run was in at that moment (the run keeps a small timeline of when those changed). Work that spans two runs at the same moment in one session is not divided by guessing: it is reported as not assigned. Subagent usage is included once, in the stage and model it ran under, and shown as a separate share.

**Coverage.** Usage is `tracked`, `partial` (with the reasons, such as a malformed or unreadable log, a stage with no data, or work not assigned) or `not tracked` (with the reason, such as no log naming the run, or a run from before usage tracking). Stored counts are kept when a vendor later deletes its logs.

**When it is collected.** By the dashboard, in the background, when a run changes stage, rework, ticket or session and when it finishes, and again about 15 and 60 seconds later, because agents write their logs a little after the work. It recomputes the whole run, so reading twice never counts twice, and a failure never delays or stops a run. Reading is bounded in time, in the number and size of the logs, and it does not follow links out of the log folders. Pause detection (below) also reads the logs about once a minute for working runs. There is no extra service.

## Pauses

From Claude Code logs the dashboard also detects when work stopped: a usage limit (a rate-limit error message) or a context compaction (a `compact_boundary` line). It keeps only the kind and the time. While the latest pause has no later user or assistant activity and the run is `running`, the dashboard sets the run `blocked` with the reason "Usage limit reached" or "Context compaction in progress" and records a Blocked event; once activity follows, it sets the run `running` again, clears the reason and records a Resumed event. It never changes a block whose reason the agent set, a done run, or a run the agent updated after the pause began. A block it set follows the current pause (a compaction after a usage limit changes the reason) and is cleared when the log shows no pause any more, but only when usage tracking is on and the logs were found and read completely: with tracking off, no logs, or a read that timed out or hit its limit, the block stays. Stretches of more than 10 minutes with no activity that no pause explains are shown as idle gaps. Pauses and idle gaps appear in the run details (for example "Usage limit reached · resumed after 3 h", "Context compaction · resumed after 5 s", "Idle 42 min"; the blocking reason during a compaction reads "Context compaction in progress") and under "Pauses" in `jidoka run inspect` (`usage.pauses` and `usage.idle` in `--json`). The dashboard checks working runs and runs it blocked this way about once a minute, so no agent update is needed, and stops watching a run that has had no update for 7 days. Codex and Copilot logs are not checked for pauses. Copilot's `events.jsonl` has no usage-limit or compaction event type to detect: across the sessions inspected it holds only event types such as `session.start`, `session.info`, `session.shutdown`, `model.*`, `assistant.*`, `tool.*` and `system.notification`, none of them an error or compaction. Copilot runs are therefore never blocked as paused, and only idle gaps show.

**Opt out** with `jidoka dashboard --no-usage`, or by starting the dashboard with `JIDOKA_USAGE=off`. Runs without counts then show `not tracked` and say why; counts already collected are kept.

**What has been validated.** Claude Code and Codex logs were inspected on a real machine, and all three formats are covered by fixture tests that need no agent installed. Copilot's `session.usage_record` events were checked against a real Copilot CLI session, including a subagent running on another model: their fields, the `sub-agent` initiator, the effort of each call and the rule that cache reads and writes are counted inside the input all match what the reader expects. Codex's `cache_write_input_tokens` was zero in every sample, so whether it is part of Codex's input is unvalidated; it is treated as included, like Copilot's. Agent log formats are not a stable interface: if one changes, the affected logs show as `partial` or `not tracked` instead of wrong numbers.

## Request analysis

`jidoka run requests <id>` shows how a run's model requests split over what they did, so you can see which steps cost the most requests. `jidoka run requests --all` pools many runs and shows how each category spreads over them. Add `--json` to either for the same figures as data. It reads the session logs when you call it and stores nothing. Of each request it keeps the time, the token counts and a category; no command text, tool output, prompt or path is kept or printed.

The counting rules:

- **Unit.** A model request is one response of the model. Claude Code writes a response once per content block, so a response that appears several times counts once, with the largest value of each token count.
- **Which run.** A session belongs to a run when its id was recorded on the run, or when a Bash command in it runs `jidoka run update <id>`. A run id in tool output, in a file or in a prompt does not count, and `inspect` and `stats` do not claim it. A command that only names the update, such as a `grep` or an `echo`, or text inside quotes, does not claim it either. The id may be a variable that an earlier command on the same line sets to a literal (`R=123 && jidoka run update $R ...`). A value that comes from a file or another command (`R=$(cat file)`) cannot be known here, so such a run is found through the session id recorded on the run, which Claude Code adds automatically. A request counts for a run when it falls inside the run's time, as the token usage does.
- **Overlapping runs.** A request that two runs working at the same time could both claim is in neither run. It is shown as not assigned.
- **Categories.** Each request has one category, taken from the first match in this order. The commands are read from the start of each part of a shell line, after env assignments and the words that only wrap a command (listed below).
  - Workspace: `git worktree` (other than `list`), `git clone`, `git symbolic-ref` and `jidoka run start`.
  - Commit: `git commit` and `git add`.
  - PR creation and push: `git push`, `gh pr create`, `gh pr edit`, `az repos pr create` and `az repos pr update`.
  - PR synchronization: `git fetch`, `git merge`, `git merge-base`, `git pull`, and `gh pr view` that asks for `mergeStateStatus`.
  - CI watch: `gh pr checks`, `gh run watch`, `gh run view`, `gh run list`, `gh api` calls on `actions/runs` or `check-runs`, `az pipelines runs`, `az repos pr policy list`, and `az devops invoke` on pull request statuses (`pullRequestStatuses`, `pullRequestIterationStatuses`). Other `az` commands, such as `az boards`, fall under reading, editing, analysis like any other tool call.
  - Verification: `cargo` with `test`, `fmt`, `clippy`, `build`, `check` or `nextest`; `rustfmt`; `pytest`; `npm`, `pnpm`, `yarn` and `bun` with `test`, `lint`, `build` (or `run` followed by `test`, `lint`, `build` or `check`); `go` with `test`, `vet` or `build`; `dotnet` with `test` or `build`; `make` with `test`, `check` or `lint`; and any `verify.sh`.
  - Continuation check: `jidoka run inspect`, `jidoka run check`, `git worktree list` and `git rev-parse --git-common-dir`.

  A request whose only command is `jidoka run update` is standalone reporting, any other tool call is reading, editing, analysis, and a request with no tool call is text only. Commands are split at `&&`, `||`, `;`, `|` and line ends outside quotes, the lines of a here-document are ignored, and only the first 32 words of a command are read. The words that only wrap a command are skipped: `sudo`, `time`, `command`, `exec`, `nohup`, `env` and `timeout` with their options (and the duration), the shell keywords `if`, `then`, `do`, `else`, `elif`, `while` and `until`, `!`, and an opening parenthesis or brace. Comments are ignored. A command substitution, `$(...)` or backticks, counts as one word of its command, and the commands inside it are classified too, because they run; a read-only helper in a substitution (`cat file`, `date`, `git rev-parse`) or after a pipe (`| tail -1`, `| grep`) does not make a report count as chained, but any other program there (`git apply`, `xargs`, `tee`, a script) is work of its own. The request that runs `jidoka run start` is written before the run exists, so a workspace request up to two minutes before the run's first mark counts for the run. The reader sees only the commands the agent types: what a script runs (`python3 - <<'EOF'`) is invisible, and syntax such as `case`, functions and aliases is not understood.
- **Reporting.** A `jidoka run update` chained to other commands does not decide the category: the request counts in the category of the other work and is also counted as chained reporting. That count sits beside the categories, so the category shares still add up to 100%. The table also gives the number of requests that fit more than one category, so you can see how much the order decides.
- **Tool output.** For each request, the bytes of text its tool calls returned, summed over its calls. Each category shows the total and the most one request got. Images and other non-text results are not counted.
- **Pooled view.** `--all` classes each run from its own data: completed (done, with fully tracked token usage), partial (done, but its usage is partial, missing or has stages with no data) or open (still running). It pools completed runs only; `--include-partial` adds the other two, and `--exclude <id>`, which you can repeat, drops a run, such as a development run. Jidoka cannot tell a development run from a production run. Runs it leaves out are listed with the reason, and so is a run for which no requests were found. For each category it shows the median, the 25th and 75th percentile (interpolated between the nearest runs), the minimum and the maximum of requests per run, counted over every pooled run so that a run without the category counts as zero. It also shows the pooled requests and their share, the share of fresh tokens, and the four token columns. The four token types are never added together; the fresh share is the one exception, and it uses Jidoka's usual definition of fresh tokens (input excluding cache reads, plus cache writes and output). The number of runs is in the heading, and a sample under ten runs is called small.
- **Tokens.** Input, cache read, cache write and output are separate columns and are not added together, except for the fresh share of the pooled view. `n/a` means the log did not report a count.
- **Subagents.** The requests of subagents come from the session's subagent logs. They are categorized by their own commands and shown on their own lines, marked `(subagents)`, and the total has an `of which subagents` line. A response that both a session and its subagent log hold counts once. A session with no subagent logs is reported as coordinator-only.
- **Codex.** Codex sessions are read from their rollout files. A response ends at its token record; the tool calls since the previous record belong to it, and their results, which come later, add their text to it. A command runs through a small JavaScript snippet, `tools.exec_command({cmd: "..."})`; the snippet is scanned for string literals and never run. A `cmd` that is a single plain literal (with its JavaScript escapes decoded) is classified like a Bash command. A `cmd` that is a variable, a concatenation or a template with `${...}` cannot be read, and neither can anything else Codex calls (`apply_patch`, `write_stdin`, web calls, the agent tools): each counts as a tool call that is not a command. A subagent rollout starts with a copy of its parent's history, which is not its own work, so unfinished calls are dropped when a turn starts. A Codex session claims a run in two ways. `jidoka run begin|start|update` records the session ids Codex puts in the environment (`CODEX_SESSION_ID`, the root session, and `CODEX_THREAD_ID`) on the run, as `CLAUDE_CODE_SESSION_ID` is for Claude Code. Otherwise the session is claimed by a command the agent ran: an executed `jidoka run update <id>` or `jidoka run sync <id>` (a `CommandExecution` item, an `exec` snippet, or the older `function_call` and `local_shell_call` shapes). Only commands are read; the id in tool output, a file the agent read, a message or an assignment alone does not claim a session. The id may come from a shell variable set to a literal, such as `R=<id>; jidoka run update $R`, `export R=<id>` in an earlier command of the same rollout, or `"${R}"`. The run requests reader uses the same rule, so both claim the same sessions. A subagent rollout (`thread_source` `subagent` or a `thread_spawn` source) belongs to its root session and counts with it, flagged as a subagent; a forked subagent that replays its parent's history adds nothing twice, because responses are counted once by `response_id`.
- **Copilot.** Copilot sessions are read from `events.jsonl`. A request is a `session.usage_record`; the `assistant.message` with the same `apiCallId` holds its tool calls. `bash` commands are classified like Bash commands, and every other tool call (`view`, `edit`, `create`, `grep`, `task` and so on, including a subagent run) is reading, editing, analysis. A request with no tool call is text only. Tool output is the text of each call's `tool.execution_complete` result, summed over the request. Subagent requests (the `sub-agent` initiator) are shown on their own lines, marked `(subagents)`. A usage record with no matching assistant message stays `not categorized`, with `n/a` for tool output; a request whose tool results are missing from the log is categorized but has `n/a` for its tool output. Only `bash` commands are read: Copilot's other shell tools count as tool calls that are not commands. A Copilot session counts for a run by the usage reader's rule: its id was recorded on the run, or its log names the run in a `jidoka run update`, `run inspect`, `run stats`, `run check`, `pr open`, `pr sync` or `pr wait` command.
