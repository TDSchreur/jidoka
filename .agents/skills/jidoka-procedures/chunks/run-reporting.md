## Run reporting

Report progress to Jidoka dashboard with the `jidoka` CLI from the run's worktree (see Workspace). Update only at the points below; do not send periodic updates.

- **Start:** before Define, create the run. Normally `jidoka run begin` does this together with the workspace (see Workspace); keep the run ID it prints. When the workspace is not made that way, run `jidoka run start "<short task title>" --agent <agent>` and keep the printed run ID. `<agent>` is the coding agent you are running in: `claude` for Claude Code, `codex` for Codex, `copilot` for Copilot CLI. Jidoka uses it to pick that agent's model-routing policy, and says on standard error when it applies none; keep that for the Stage summaries. If the command stops with a message about the policy, tell the user what it says and stop. If the server is not running, start `jidoka dashboard` as a background process, then retry once. If a different or outdated server occupies the port, or the CLI rejects an option (including `--agent`), report that it needs to be stopped or upgraded.
- **Stage:** leave a stage with `jidoka run advance <id> --summary <stage>="<one or two sentences>" --activity "<what the next stage does>"`. It checks the gates and saves the summary and activity with the successful transition. If the gates refuse the move, address the blockers and include the summary and activity when retrying. Revise them if the candidate or next step changed. On success it prints the next stage's instructions as `jidoka run next <id>` would (`--json` prints them as data). Do not run a separate `jidoka run next` or `jidoka run update` for that. Read the whole output of `jidoka run advance` and `jidoka run next`; never cut it with `head`, `sed`, `tail` or similar, because later sections hold required steps.
- **Milestone:** after a meaningful milestone, such as tickets created or checks passing, run `jidoka run update <id> --activity "<short phrase>"`. Keep the activity to one short line without secrets.
- **Ticket:** mark a listed ticket active with `--ticket-status <reference>=in-progress` for either a tracker URL or a local reference. Mark it `done` when finished or `pending` if stopping work on that attempt. Only one ticket can be in progress.
- **Run reports:** when a skill is used for the run outside a listed ticket, append `--run-report skill "<skill-name>"` to the next run update. At meaningful milestones outside a listed ticket, append `--run-report activity "<short outcome>"`. Repeat for multiple reports, including known delegated work. Report the workflow and procedures used at the first update after run creation, including skills loaded before it. Reports are retained and may be incomplete; never include secrets or transcripts.
- **Ticket reports:** once the ticket is listed, append `--ticket-report "<reference>" skill "<skill-name>"` when a skill is used for it and `--ticket-report "<reference>" activity "<short outcome>"` at meaningful milestones. Repeat the option for multiple reports. Use the ticket reference from the list, including local references, and the current stage; reports are retained and may be incomplete. Do not include secrets or transcripts. Include reports from delegated work when known.
- **Blocked:** when outside input is needed, run `jidoka run block <id> --reason "<what is needed>"`. When work resumes, run `jidoka run resume <id> --source "<what let work resume>"`. Ordinary progress reports preserve both status and the reason for a block.
- **Context:** record what a new session needs to continue the run, with `jidoka run update <id>` options, only through the CLI and never by editing Jidoka's files. Each of these is a reference or a short summary, never a transcript, a secret or a token. Options left out keep their value; `--clear-<name>` removes one.
  - Once the worktree exists (`jidoka run begin` records these for you): `--mode <the workflow's name> --worktree <absolute path> --branch <branch> --base-commit <commit the worktree started from>`. Once recorded, the workflow mode is fixed.
  - Once a spec or tickets exist: `--spec <url or absolute path>`, and one `--ticket "<reference> <title>"` per ticket in order (list them all each time; their statuses are kept). Record a local spec or ticket file by its absolute path, so the dashboard can open it. If the work has no tickets, record `--unticketed` before Build.
  - When a stage ends: `--summary <define|build|check|finish>=<one or two sentences>`, normally given to `jidoka run advance`. Summaries of earlier stages are kept.
  - When the pull request exists: `--pr <url>`.
- **Done:** once the pull request is open and its CI is green (or the project has no CI), run `jidoka run advance <id> --summary finish="<what shipped>" --activity "Opened <pull request URL>"`.

Options that are left out keep their current value. If the server or an update fails, report the failure rather than claiming progress is tracked.

When the installed `jidoka` rejects a command or an option that these procedures use, such as `run begin`, `run check` or `pr sync`, the skills and the binary are out of step. Do not work around it by hand: report that Jidoka needs upgrading with `jidoka install` from a current release, mark the run blocked with that reason if the run exists, and stop.
