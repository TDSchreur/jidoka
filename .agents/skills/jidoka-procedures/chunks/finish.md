## Finish

Use `jidoka-pr` to write the pull request description, and give it the review record for its Review section, so reviewers see what was checked without the agent session. From Check: take the Findings from `jidoka run inspect` (id, check, location, text, outcome, reason and fix commit), and give each check that ran, the commit it reviewed, its outcome and the Reworks it caused, and each skipped check with the reason. In a workflow without Check, say that no review ran before the pull request. Name every deferred Finding with its reason, and list any Finding still open that the user chose to finish with. Commit anything still uncommitted that belongs to the change as a new commit. Verify the final commit before pushing: reuse the latest passing full verification when the final commit contains exactly the checked code and its relevant inputs are unchanged, otherwise run the project's verification on it. Report the result; do not open the pull request while a check fails or cannot run. Then follow the `jidoka-procedures/references/pull-request-and-ci.md` file in the installed skills to open the pull request, and read it again while watching CI. The Finish report tells the user to run `jidoka run cleanup <id>` once the pull request merges.

If the pull request merges while CI is being checked, run `jidoka run sync <id>` to reconcile its state, then follow the reported cleanup instructions.
