## Finish

Open the pull request with `jidoka pr open` and watch CI with `jidoka pr wait`, as Pull request and CI below describes; do not call `gh` or `az` directly for that (for another host, follow that section).

Use `jidoka-pr` to write the pull request description, and give it the review record for its Review section, so reviewers see what was checked without the agent session. From Check: take the Findings from `jidoka run inspect` (id, check, location, text, outcome, reason and fix commit), and give each check that ran, the commit it reviewed, its outcome and the Reworks it caused, and each skipped check with the reason. In a workflow without Check, say that no review ran before the pull request. Name every deferred Finding with its reason, and list any Finding still open that the user chose to finish with. Commit anything still uncommitted that belongs to the change as a new commit. Verify the final commit before pushing: reuse the latest passing full verification when the final commit contains exactly the checked code and its relevant inputs are unchanged, otherwise run the project's verification on it. Report the result; do not open the pull request while a check fails or cannot run. Then follow Pull request and CI, included below, to open the pull request and watch CI. The Finish report tells the user to run `jidoka run cleanup <id>` once the pull request merges, and to start the next run in a fresh agent session (`/clear` in Claude Code, `/new` in Codex, `/clear` in Copilot CLI) so its context starts small.

If the pull request merges while CI is being checked, run `jidoka run sync <id>` to reconcile its state, then follow the reported cleanup instructions.

When `jidoka run next` prints a Change group, this run is one of several related changes. Its prerequisites are advisory: they never block Finish or the pull request. Report each outstanding prerequisite to the user with its status, and advise them to wait for those before merging. Tell the user that the pull request's link belongs in the group's shared spec, and that whoever confirms or reopens a milestone with `jidoka group confirm` or `jidoka group reopen` also updates its status in that spec. A prerequisite the run's pull request must wait on is described in the pull request, as Pull request and CI says.
