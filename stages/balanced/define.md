# Balanced: Define

When the request is clear and bounded, use it as the spec and state the plan and explicit acceptance criteria in the conversation; no tracker setup is needed for that. Otherwise follow Tracker setup in the shared procedures included below and use `jidoka-to-spec` once to write a concise spec from the request and the code, without interviewing the user, stating explicit acceptance criteria either way. Before Build, if the plan and criteria exist only in the conversation, follow Saving the plan in the shared procedures included below.

Use `jidoka-to-tickets` only when the work has multiple pieces that benefit from separate tracking. Use `jidoka-grill-with-docs` only when an ambiguity blocks implementation, and limit it to that ambiguity. Reuse existing specs and tickets rather than recreating them. Reading or publishing specs and tickets in the tracker needs Tracker setup first.

When these artifacts are needed, store them in the tracker configured in `docs/agents/issue-tracker.md`.

Follow Define rules in the shared procedures included below for the whole Define stage.
